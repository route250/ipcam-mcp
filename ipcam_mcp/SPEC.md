# IPカメラサーバー v1 仕様書

## 対象と起動

Ubuntu上のPython FastAPIサーバーが、同一LAN内のWTW-IPW308TTW/Bを1台管理するワン。
ブラウザーとMCPは同じサーバープロセスに接続し、最新映像、位置、温湿度、パンチルトの制御権を共有するワン。
カメラへの通信にはTCP 90、TCP 10081、探索通知の受信にはUDP 6667を使うワン。

実装の起動入口はリポジトリのルートから実行する `python -m ipcam_mcp --config .config/ipcam-server.json` とするワン。
FastAPI、Uvicorn、既存のMCP Python SDK、システムのFFmpegを使用し、Python依存関係は実装時に固定するワン。
Uvicornは既定で `127.0.0.1:8000` の1ワーカーで起動し、`--host` と `--port` でIPv4の待ち受けアドレスとポートを変更できるワン。
`localhost` と `127.0.0.1`、個別の待ち受けアドレスをHTTPのHostとして許可し、LANで使うホスト名やIPアドレスは `--allowed-host` を繰り返して追加するワン。
Hostのポート番号は指定した待ち受けポートと一致する場合だけ許可するワン。
ブラウザー、MCPクライアントともに信頼済みLAN内の利用者を前提とするワン。
OriginヘッダーがあるHTTP要求は同一オリジンのみ許可し、操作用WebSocketには同一オリジンのOriginを必須とするワン。
ブラウザーの部品はサーバーから配信し、クラウドAPIや外部CDNへの要求を発行しないワン。

| 設定キー | 型と意味 |
| --- | --- |
| `lan_cidr` | 必須。サーバーのLANインターフェースが接続するRFC 1918内のIPv4 CIDRワン |
| `camera_host` | 省略可。手動指定のカメラIPv4アドレスワン |
| `device_id` | 省略可。探索通知を照合するTuyaの `gwId` ワン |
| `calibration_path` | 旧設定との互換性のため受け付けるキー。値は使用しないワン |

`camera_host` または `device_id` の少なくとも一方が必要ワン。
接続先は指定CIDR内のユニキャストIPv4に限定し、ブラウザーやMCPの入力から接続先を変更できるようにしないワン。
設定の構文や必須項目の誤りは起動エラーとし、カメラの未接続は起動後の状態として公開するワン。
設定はサーバー起動時に読み込むワン。

SDカードの準備とサーバーの起動手順は [README](../README.md) に記載するワン。

## カメラの探索と接続

起動時は手動指定のアドレス、前回確認したアドレス、探索通知から得たアドレスの順に候補を試すワン。
手動指定に失敗しても、`device_id` が設定されていれば保存済み候補と探索に進むワン。
保存済みアドレスは `device_id` が設定され、保存時の `device_id` と `lan_cidr` が現在の設定と一致する場合に限り再利用するワン。
探索時はUDP 6667の受信パケットを既存のTuya探索形式で解釈し、送信元IPv4と通知内のIPが一致し、`gwId` が設定値と一致する候補を受理するワン。
探索通知はアドレス候補の取得に使い、端末の認証には使用しないワン。
本機からの探索通知は過去の20秒間の受信試験で観測されていないため、通知を受信できない環境では `camera_host` を設定するワン。

候補の採用条件は、以下の3項目すべての成功とするワン。

1. TCP 10081の `/device_model.txt` を直接取得し、末尾の改行を除いた型番が `IPC-G3B2D0-TY` と一致するワン。
2. TCP 90のINFログインに成功し、Ubuntuの現在UTCをUnix秒で `set TimeInfo`（method 0）に渡して応答を受け取るワン。
3. TCP 10081の `/motorPosition` を取得し、パンとチルトのステップ値を検証できるワン。

位置ファイルがHTTP 404の場合は、その接続先についてサーバー起動中に最大1回、上へ0.1秒、停止、下へ0.1秒、停止を要求するワン。
0.5秒待って位置ファイルを再取得し、失敗した場合は採用せず通常の再試行を続けるワン。
移動や停止の応答を確認できない場合は次の移動を行わず、同じ起動中に動作を繰り返さないワン。
404以外のHTTPエラー、通信エラー、不正な位置データではモーターを動かさないワン。

INFログインと受信フレームの検証は [既存の映像取得処理](../tools/hank_camera.py) に従うワン。
時刻設定には [既存のパケット生成処理](../tools/hank_feature_packets.py) を再利用し、コマンド101、本文84バイト、verbと機能名の一致、status=0を確認するワン。
ファームウェアは時計更新の戻り値を応答に反映しないため、応答は要求の受理として扱うワン。
時刻設定は候補採用時に行い、画像や測定値の時刻はUbuntu側で付けるワン。

採用したアドレスは設定ファイルと同じディレクトリの `ipcam-server-state.json` に、`device_id` と `lan_cidr` とともに一時ファイル経由の置換で保存するワン。
状態ファイルの書き込みに失敗した場合はログに記録し、その接続はメモリー上で継続するワン。
探索、候補検証、映像取得はバックグラウンドで動かし、カメラが見つかるまでWeb画面とMCPの情報取得を利用できるようにするワン。
候補検証に失敗した場合は次の候補へ進み、候補を使い切ったら1、2、4、8、16、30秒の間隔で再試行し、以後は30秒間隔とするワン。
接続中は別の探索通知で接続先を切り替えないワン。
映像が切れたら同じ接続先の映像を上記間隔で再開し、3回連続で有効なJPEGを受け取れなければ、動作中のパンチルトを停止処理へ移してから候補検証へ戻るワン。
位置または温湿度だけの取得失敗では映像の接続を維持するワン。

## 映像と測定値

カメラへの映像接続は1本とし、待機中も受信を続けるワン。
TCP 90のINF3で640×360のH.264サブ映像を要求し、映像ペイロードをFFmpegで逐次デコードしてJPEGに変換するワン。
音声ペイロードは破棄するワン。
フレームの検証に失敗した場合、接続が切れた場合、または有効なJPEGを5秒間受け取れなかった場合は、ソケットとFFmpegを終了して再接続するワン。
この5秒は映像開始要求の送信から計測し、有効なJPEGを受信するたびに計測をやり直すワン。

サーバーは最新JPEGとその時点の測定値を1組としてメモリー上で置換し、JPEGと測定値の組を不可分に読み出せるようにするワン。
JPEGは1枚1 MiB以下とし、画像や測定値をファイルに記録しないワン。
配信クライアントごとに送信待ちのJPEGを積まず、送信可能になった時点で最新の1枚を選ぶワン。
JPEGの時刻はサーバーが完全なJPEGを受け取った時刻とするワン。

位置と温湿度は別々に1秒周期で取得を開始し、前回の同種要求が終わっていない周期は飛ばすワン。
位置の取得はTCP 10081の `/motorPosition` を使うワン。
パンの角度は右を正とし、2020ステップを0度として約11.5493ステップ/度で換算するワン。
チルトの角度は上を正とし、891ステップを0度として約7.8333ステップ/度で換算するワン。
ステップ値から換算した角度は推定値ワン。

温湿度は [既存の取得処理](../tools/hank_environment.py) を使用してTCP 90の `TemperatureHumidityInfo` から取得するワン。
参照時刻を `t` として、取得完了が `(t - 5秒, t]` に入る有効なサンプルの単純平均を温度と湿度それぞれに適用するワン。
その区間に有効サンプルが1件あれば平均を返し、0件なら値を `null` とするワン。
通信失敗、形式不正、非有限値、範囲外湿度、温度と湿度が同時に0の応答はサンプルに含めないワン。
温度はカメラ側で補正済みの値を使うワン。

鮮度、平均窓、リトライは単調時計で判定し、公開時刻はUTCのRFC 3339形式とするワン。
JPEGに添える位置はJPEG受信時点で取得済みの最新値とし、温湿度の平均窓はJPEG受信時刻を基準にするワン。
現在情報では両方とも要求処理時刻を基準にするワン。
接続先を再検証する際はJPEGと測定履歴を消去し、接続切替前に始まった要求の結果を破棄するワン。

## 共通の状態データ

`GET /api/status`、MCPの情報取得、静止画のメタデータは以下の形式を使うワン。
静止画では `state` から `environment` までが画像受信時点の値となり、`at_utc` は画像の受信時刻となるワン。

| フィールド | 型と意味 |
| --- | --- |
| `at_utc` | 文字列。状態データの基準時刻ワン |
| `state` | `discovering`（候補検証中または未採用）、`connecting`（候補採用済みで映像の待機または再接続中）、`ready`（鮮度内のJPEGを配信可能）ワン |
| `frame` | `null` または `{id, received_at_utc, width, height}`。IDは起動中に単調増加する整数。寸法は640、360ワン |
| `ptz_state` | `idle`、`manual`、`goto`、`stopping`、`stop_unconfirmed`、`homing`、`homing_unconfirmed` のいずれかワン |
| `position` | `{status, sampled_at_utc, pan_steps, tilt_steps, pan_degrees, tilt_degrees}` ワン |
| `environment` | `{status, sampled_at_utc, temperature_c, relative_humidity_percent, sample_count}` ワン |

`position.status` は `ok` または `unavailable`とするワン。
基準時刻から2秒以内に取得した有効なステップ値があれば、整数のステップ値と取得完了時刻を返すワン。
有効なステップ値があれば `ok` と推定角度を返すワン。
有効なステップ値がない場合は `unavailable` とし、時刻と数値は `null` とするワン。
移動中の位置は `/motorPosition` がその時点までに返した値で、停止後に確認した到達位置は位置指定の結果で返すワン。

`environment.status` は有効サンプルがあれば `ok`、0件なら `unavailable` とするワン。
`sampled_at_utc` は平均に含まれる最新サンプルの取得完了時刻とし、0件なら `null` とするワン。
`frame` は最新JPEGの年齢が5秒未満かつ映像接続が継続中の場合に公開するワン。
切断検知時に最新JPEGを無効にし、同一接続先へ再接続する場合は位置と温湿度の履歴を各項目の鮮度期限まで使用できるワン。

## ブラウザー

| パス | 動作 |
| --- | --- |
| `GET /` | 映像、方向パッド、ステップまたは角度での位置指定、推定角度、温度と相対湿度を表示するワン |
| `GET /api/status` | 共通の状態データをJSONで返すワン。未接続でもHTTP 200とするワン |
| `GET /api/stream.mjpg` | `multipart/x-mixed-replace` の各パートを `image/jpeg` として返すワン。接続開始時に利用できるJPEGがなければHTTP 503とし、配信中に無効になったら応答を閉じるワン |
| `WS /api/ptz` | 方向パッドの開始、更新、停止、原点復帰、位置指定を受け付けるワン |

状態と映像の応答に `Cache-Control: no-store` を付けるワン。
画面の映像枠は標準で640×360 CSS pxとし、狭い画面ではブラウザーの表示だけを16:9のまま縮小するワン。
配信用と静止画用のJPEGは、実機のサブ映像と同じ640×360で生成するワン。
画面は1秒ごとに状態を取得し、`frame` が `null` の間は画像を隠して接続状態を表示するワン。
`frame` が存在し、映像の配信接続がなければ、同じ周期で配信接続を試みるワン。
角度や温湿度に `null` が入った場合は取得不可と表示するワン。
角度、温度、湿度は小数1桁とし、単位は `°`、`℃`、`%RH` とするワン。

円形パッドはポインターの押下時にキャプチャし、押下中の座標をパッド中心からの変位で判定するワン。
中心から半径の20%以内は停止、外側は絶対値の大きい軸の方向とし、同値では左右を優先するワン。
ドラッグ中に方向が変わった場合は停止ACKを受けてから新しい方向へ移動するワン。
ボタン解放、`pointercancel`、ポインターキャプチャ喪失、フォーカス喪失、ページ非表示では停止メッセージを送信するワン。
WebSocketの切断を検知したサーバーも、その接続が所有する手動移動を停止するワン。

方向パッドの操作メッセージは `{"type":"drive","direction":"up"}` または `{"type":"stop"}` とするワン。
方向は `up`、`down`、`left`、`right` の4値とし、押下中に同じ方向の `drive` を100 msごとに送るワン。
サーバーはWebSocket接続を操作の所有者とし、同じ方向の更新では操作期限だけを延長するワン。
最後の有効な更新から500 msで停止処理を開始するワン。
1回の連続操作は最初の `drive` から10秒で終了し、同じ押下の更新による再始動は、`stop` の受信または接続終了まで拒否するワン。
サーバーは各メッセージに `{"ok":true,"ptz_state":"manual"}` 形式で受付を返し、状態変化は `{"type":"state","ptz_state":"idle"}` 形式で通知するワン。
受付の成功は制御権と期限の設定を示すワン。
メッセージの拒否には `{"ok":false,"code":"busy","message":"..."}` 形式で応答するワン。
受付後の障害は同じオブジェクトに `"type":"error"` を加えて通知するワン。

「原点復帰」ボタンは `{"type":"homing"}` を送るワン。
方向パッドと同じ排他制御を使い、現在の位置を読み取れた場合にTCP 90のINF15で `Z` を1回送るワン。
カメラは両軸を動かし、ファームウェアの復帰位置へ戻るワン。
受付された原点復帰はカメラ側で継続するため、WebSocketの切断後もサーバーは完了を監視するワン。

開始時に取得できた `/motorPosition` がHTTP 404になるまで、最大30秒確認するワン。
原点復帰中はステップと角度を取得不可とするワン。
HTTP 404を確認したら、右、左の順に各0.1秒動かして、ファームウェアに位置ファイルを再生成させるワン。
それぞれの移動後に停止ACKを確認し、同じステップ値を3回連続で取得してから、最終の停止ACKを確認するワン。
この確認が終わるまで操作権を保持し、ステップ値の再取得に成功したら要求元に `{"type":"homing_result","ok":true}` を通知するワン。
30秒以内に完了を観測できなければ `homing_unconfirmed` に移り、追加のモーター操作を拒否するワン。
その場合は実機が停止したことを確認してからサーバーを再起動するワン。

画面の位置指定は度の場合に `{"type":"goto","pan_degrees":30}`、ステップの場合に `{"type":"goto_steps","pan_steps":2300}` の形式で送るワン。
WebSocketは `goto_result` イベントで成否と、成功時にはMCPと同じステップ値と誤差を通知するワン。
要求元のWebSocketが切断された場合は進行中の指定移動を取り消すワン。

## 音声再生

`GET /audio` はカメラ1台につき1本のSSEセッションを開き、最初に `event: session` と `{"session":"..."}` を送るワン。
接続中にもう1本開くとHTTP 409を返すワン。
以下のPOSTにはSSEで受け取った値を `X-Audio-Session` に指定するワン。

| HTTP | 処理 |
| --- | --- |
| `POST /audio` | `Content-Type: application/octet-stream` の本文に8 kHz・モノラル・符号付き16 bitリトルエンディアンの生PCMを渡すワン。 `X-Audio-Length` にサンプル数、任意の `X-Audio-Indexes` に区切り位置を昇順のカンマ区切りで指定するワン。受理するとHTTP 202と `{"id":1}` を返すワン |
| `POST /audio/pause` | 現在のカメラへの送信を停止するワン。一時停止中も音声を受け付けるワン |
| `POST /audio/resume` | 保留中の音声の続きから再開し、その後にキューの音声を処理するワン |
| `POST /audio/cancel` | 現在の送信を中止してキューを全件破棄し、対象IDごとに `end` を送るワン。一時停止状態は維持するワン |

IDはセッション内で1から始まる連番で、音声は受理順に処理するワン。
受理できる音声は1件あたり1〜480,000サンプル（最大60秒）で、本文のバイト数は `X-Audio-Length` の2倍ワン。
区切りは最大128件で、位置の範囲は0〜`X-Audio-Length` ワン。
同時に処理できるのはアップロード中と終了通知の送信待ちを含めて32件で、上限ではHTTP 429を返すワン。
制御POSTはHTTP 204を返すワン。
SSEの切断を検知した場合は送信を停止してキューを破棄するワン。

| SSEイベント | JSONデータ |
| --- | --- |
| `start` | `{"id":1}`。カメラの開始ACKと先頭フレームの送信後に1回送るワン |
| `index` | `{"id":1,"index":8000}`。フレームの送信時刻とサンプル位置をもとに通知するワン |
| `end` | `{"id":1,"length":16000,"reason":"completed"}`。長さは受理時のサンプル数で、理由は `completed`、`cancelled`、`failed` のいずれかワン |

受け取ったPCMはワーカースレッドで一括してG.711 μ-lawに変換してからキューに入れるワン。
カメラへの接続と320サンプル単位の送信は専用スレッドで実行し、HTTPのイベントループには開始と再生位置を通知するワン。
先頭の2フレームは待機を挟まず、3フレーム目以降は最初の送信完了時刻を基準に40 ms、80 ms、120 msと送信予定時刻を定めるワン。
予定から40 ms以上遅れた場合は、その送信完了時刻を基準に以降の予定を組み直すワン。
最後のフレームまでの再生予定時刻が経過した時点でサーバーが終了を判定するワン。
一時停止時はカメラとの再生接続を閉じるワン。再開位置はサーバーが時刻の経過を確認した最後のフレーム末尾または区切り位置のため、停止直前に送ったデータが再度送られる場合があるワン。
カメラがすでに受け取った音声の停止時刻はサーバーから確認できないワン。

## MCP

FastAPIと同じプロセスの `/mcp` にMCP Streamable HTTPを公開するワン。
MCP SDKのセッションマネージャーはFastAPIの起動と終了に合わせて実行するワン。
ブラウザー用ストリームとMCPは同じキャッシュとパンチルト制御を使用するワン。

| ツール | 入力 | 成功時の結果 |
| --- | --- | --- |
| `camera_get_info` | 引数なしワン | 要求時点の共通状態データを `structuredContent` で返すワン |
| `camera_snapshot` | 引数なしワン | 最新フレームのJPEGをMCPの画像コンテンツとして返し、同じフレームの共通状態データを `structuredContent` に入れるワン。利用できるJPEGがない場合は `frame_unavailable` ワン |
| `camera_goto` | `pan_degrees` と `tilt_degrees` は省略可能な有限のJSON数値で、少なくとも一方が必要ワン | `reached: true`、`position`、`target_steps`、`error_steps`、`tolerance_steps: 20` を `structuredContent` で返すワン |
| `camera_goto_steps` | `pan_steps` は0〜4100、`tilt_steps` は0〜1140の整数で、少なくとも一方が必要ワン | `camera_goto` と同じ形式ワン |

`camera_goto` のパンは −177.5〜+177.5°、チルトは −30〜+90°を入力範囲とし、換算後の目標値もパン0〜4100、チルト0〜1140ステップの範囲内であることを移動前に検証するワン。
省略した軸の目標は、操作権取得直後に読み取ったステップ値とするワン。
接続先または操作開始時の位置取得を利用できない場合は、対応するエラーを返して移動要求を送らないワン。
結果の `target_steps` と `error_steps` は `pan_steps` と `tilt_steps` をキーとする整数値のJSONオブジェクトで、誤差は実測値から目標値を引いた値とするワン。

## パンチルトの排他制御と停止

ブラウザーとMCPで共通の排他制御を持ち、カメラへの移動要求は1件ずつ処理するワン。
操作中の別クライアントからの移動要求は待ち行列に積まず、`busy` を返すワン。
ブラウザーの停止はその接続が所有する手動操作に適用するワン。
保留中の方向変更がある場合は停止を優先して破棄し、その操作からの移動要求を打ち切るワン。
稼働中は既存CLIや別のMCPサーバーから同じカメラのモーターを操作しない運用とするワン。

手動操作はTCP 90のINF15、速度値1の1軸方向要求を使用するワン。
開始前と方向反転を含む方向変更前に、新しい認証済み接続で `H` を送り、停止ACKを確認するワン。
指定移動はステップ差の絶対値を移動方向の速度で割り、最短0.02秒の時間を求めるワン。
同じ軸で直前と逆方向に動かす場合だけ、パンは0.300秒、チルトは0.390秒を加えるワン。
方向パッドで送り出した方向も軸別に記録し、原点復帰を送る時点やカメラ接続を失ったときに履歴を破棄するワン。
方向が不明なら加算せず、各移動を上限10秒に収めて1軸ずつ動かすワン。
各移動を停止した後に3回連続で同じステップ値を確認するワン。
初回の移動後に許容差20ステップを超える軸があれば、残りの差と更新した速度から時間を計算し直して最大3回補正するワン。
両軸が許容差以内で、最終の停止ACKを受けた場合に成功を返すワン。
指定移動の期限は操作権取得から60秒とするワン。
期限超過、要求の取消、サーバー終了、位置フィードバックの喪失では新しい移動要求を打ち切り、停止処理へ移るワン。

移動速度の初期値はパン方向が約388.59ステップ/秒、チルト方向が235ステップ/秒ワン。
方向パッドの操作では、移動開始と停止の送信間隔および実測ステップ差から速度を計算するワン。
指定移動では各軸の初回に指示した時間と実測ステップ差を使うワン。
現在の速度推定から計算した移動量との差が20ステップを超え、同じ符号の誤差が同じ移動方向で3件続いたときに更新するワン。
3件の最大速度が最小速度の1.25倍以内なら、その中央値の25%と前の推定値の75%を合成し、接続先IPと方向ごとに保持するワン。
初回に許容差に入った場合はその方向の候補を破棄するワン。
反転時、指定移動の補正パルス、0.25秒未満、指令と逆方向または移動なし、可動端への到達、初期速度の0.25倍未満または4倍超の測定は速度更新に使わないワン。
更新値はサーバーの起動中のメモリーで保持するワン。

停止ACKの待機時間は移動期限の後に加わる場合があるワン。
手動操作は映像の鮮度喪失時にも停止するワン。

タイマーと取消は移動要求のACK待ちと独立に監視し、送信直前に所有者と期限を再検証するワン。
停止処理を開始した古い操作から新しい方向要求が送信されないように、方向要求の送信と停止開始の順序を制御するワン。
停止は移動に使ったソケットと別の接続で行い、失敗時は新しい接続で1回再試行するワン。
停止処理が終わるまで操作権を保持し、2回とも失敗した場合は `stop_unconfirmed` を公開して新規移動を拒否するワン。
この状態では元の接続先に対して5秒間隔で停止要求を再試行し、停止ACKの確認後に操作を再開できるワン。
停止ACKは要求の受理を示すワン。
接続断の間の物理停止時刻は観測できないワン。

TCPの接続および個々の応答待ちのタイムアウトは1秒とし、動画フレームの継続監視には映像節の5秒の制限を適用するワン。
ソケットI/OとFFmpegの入出力はFastAPIのイベントループをブロックしないワン。
正常終了時は新規操作を拒否し、手動移動と角度指定を取り消して停止ACKの確認を試みるワン。
原点復帰中は監視を終了し、カメラ接続とFFmpegを終了するワン。

## エラーコード

MCPのツール実行エラーは `isError: true` とし、内容に `code` と `message` を含めるワン。
ブラウザーの操作エラーも同じコードを使用するワン。
通信失敗の詳細はサーバーログに記録し、応答にはカメラから受け取った生データを含めないワン。

| コード | 条件 |
| --- | --- |
| `invalid_argument` | 操作の型、方向、角度、または換算後のステップが仕様の範囲外ワン |
| `busy` | 他の操作が制御権を保持しているワン |
| `camera_unavailable` | 接続先が未採用、または手動操作や原点復帰に必要な映像が利用できないワン |
| `frame_unavailable` | 利用できるJPEGがないワン |
| `position_unavailable` | 有効な位置フィードバックを取得できないワン |
| `motion_failed` | 移動要求のACK失敗、指定位置への未到達、移動期限超過、または手動操作の期限切れワン |
| `stop_unconfirmed` | 停止の再試行後もACKを得られないワン。他の操作エラーと同時に起きた場合はこのコードを返すワン |
| `homing_unconfirmed` | 原点復帰要求の送信後、30秒以内に位置ファイルの消失を観測できないワン |
| `position_refresh_failed` | 原点復帰の完了後に、位置を再生成するための移動またはステップ値の再取得に失敗したワン |

## 受け入れ条件

- 模擬カメラで探索通知の照合、手動IPのみでの起動、異なる機種の拒否、TCP 10081の不通、時刻設定応答の不正、採用済みIPの変更を試験するワン。
- 2つのブラウザーで同時に映像を開き、MCPで静止画を取得しても、カメラへの映像接続が1本であることを確認するワン。静止画は640×360のJPEGで、画像と状態データのフレームIDが同じキャッシュ更新に由来することを確認するワン。
- 模擬時計で温湿度の5秒窓の境界、欠測、全件期限切れ、位置の2秒期限、映像の5秒期限、接続先変更によるキャッシュ破棄を試験するワン。
- 押下、方向変更、解放、タブ非表示、WebSocket切断、更新の途絶を再現するワン。解放や切断をサーバーが検知した場合は停止処理に移り、更新途絶時は最後の更新から500 msで停止処理を開始することを確認するワン。
- 模擬カメラでブラウザーとMCPを競合させ、同時に2件の移動を送信しないことを確認するワン。ステップと角度の範囲外、補正回数の上限、MCPの取消、期限超過、停止ACKの喪失、ACKを取得した後の復帰も試験するワン。
- 実機のWANアクセスを遮断したLANで、ブラウザーの映像と方向操作、MCPの情報と静止画を確認するワン。可動範囲の中央付近で両軸の小移動を試し、停止後の位置が各軸20ステップ以内であることを確認するワン。
